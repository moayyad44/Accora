# Accora — النشر، النسخ الاحتياطي، وجاهزية الإنتاج (Phase 13)

> حالة المستند: **تم التنفيذ والتحقق فعليًا للنسخ الاحتياطي والاستعادة** (تجربة حقيقية كاملة بأرقام حقيقية، موثّقة بالقسم 3). ملفات التعبئة بحاويات Docker (`Dockerfile` و`docker-compose.yml`) مكتوبة وجاهزة بالكامل، لكن ما قدرت "أشغّلها" فعليًا داخل بيئة هالجلسة الحالية لأنه برنامج Docker نفسه مو متوفر هون كخدمة تعمل — موضّح بالتفصيل بالقسم 2.

---

## 0. أولًا: ثغرة صغيرة اكتشفتها وصلّحتها — أمر تشغيل الخادم كان معطوب

لما جهّزت هاي المرحلة، اكتشفت إنه الأمر يلي المفروض يشغّل الخادم بعد البناء (`pnpm start`) كان **بيشاور على مسار غلط** ما بيطلع فيه أي ملف فعليًا — يعني لو حدا حاول يشغّل السيرفر بالطريقة "الرسمية" المفروضة كانت بتفشل فورًا. صلّحته، وجربته فعليًا بعد التصليح واشتغل صح. هاي بالضبط نوع الفحص يلي لازم يصير قبل ما نعتبر أي نظام "جاهز للإنتاج".

---

## 1. فحص جاهزية الخادم (Health Check)

`GET /health` — Endpoint جديد، لا يحتاج تسجيل دخول، غرضه الوحيد إثبات إن الخادم شغّال وقادر يوصل لقاعدة البيانات فعليًا (مش بس إنه العملية شغّالة). هاد النوع من الـ Endpoints ضروري لأي بيئة إنتاج حقيقية — أي أداة مراقبة أو موازن أحمال (Load Balancer) بتستخدمه عشان تعرف "هل هاي النسخة من الخادم جاهزة تستقبل طلبات ولا لأ".

**تم التحقق فعليًا**: شغّلت الخادم المبني فعليًا، ناديت `/health`، ورجع `{"status":"ok","timestamp":...}` برمز نجاح 200.

## 2. التعبئة بحاويات (Docker) — جاهزة، لسا ما جربتها "تشتغل" هون

جهّزت:
- **`apps/api/Dockerfile`** — بناء على مرحلتين: مرحلة تبني الكود (تثبيت المكتبات + توليد Prisma Client + الترجمة لـ JavaScript)، ثم مرحلة تشغيل نظيفة وخفيفة تحتوي بس الملفات المطلوبة فعليًا للتشغيل.
- **`docker-compose.yml`** (بجذر المشروع) — يشغّل خادم Accora مع قاعدة بيانات PostgreSQL مع بعض، بإعدادات كلها من متغيرات بيئة (`.env`) — **ولا كلمة سر واحدة مكتوبة داخل الملفات نفسها**.
- **`.env.production.example`** — نموذج جاهز تعبيه بالقيم الحقيقية قبل التشغيل (كلمة سر قاعدة البيانات، مفاتيح تشفير الدخول، إلخ).

**بصراحة كاملة معك**: بيئة العمل الحالية يلي أشتغل فيها ما فيها برنامج Docker شغّال فعليًا (البرنامج نفسه مثبت، بس ما في "خدمة" شغّالة تقدر تبني وتشغّل حاويات فعلية). يعني قدرت أكتب هاي الملفات بعناية وبناءً على بنية المشروع الفعلية (تأكدت من كل مسار وكل أمر يستخدموه يدويًا واشتغل صح)، لكن **ما قدرت أثبت لك بتجربة حقيقية إنه "docker compose up" هيشتغل من أول مرة بدون أي تعديل** — هاي نقطة لازم تتأكد منها بنفسك (أو تطلب مني أتأكد منها) أول ما يكون عندك خادم فيه Docker فعليًا يشتغل.

### طريقة التشغيل (لما يكون عندك Docker):
```bash
cp .env.production.example .env
# عدّل القيم بملف .env (كلمات سر قوية حقيقية، ليس القيم الافتراضية)
docker compose up -d --build
```

## 3. النسخ الاحتياطي والاستعادة — **مجرّبة فعليًا وبنجاح بأرقام حقيقية**

هاي أهم نقطة بهاي المرحلة، ومجرّبة بالكامل، مش بس مكتوبة نظريًا.

### أ) أخذ نسخة احتياطية
```bash
DATABASE_URL="postgresql://postgres:PASSWORD@HOST:5432/accora?schema=public" ./scripts/backup.sh
```
بيطلع ملف واحد باسم فيه التاريخ والوقت بالضبط (مثلاً `backups/accora_20260919T135604Z.dump`).

### ب) استعادة نسخة احتياطية
```bash
./scripts/restore.sh backups/accora_20260919T135604Z.dump "postgresql://postgres:PASSWORD@HOST:5432/accora?schema=public"
```

### ج) **التجربة الفعلية يلي صارت**
1. أخذت نسخة احتياطية حقيقية من قاعدة بيانات فيها بيانات فعلية (30 شركة، 36 مستخدم، 126 قيد محاسبي بـ314 سطر، 50 فاتورة شراء، 136 سجل تدقيق، 8 طلبات اعتماد — كلها بيانات حقيقية من اختبارات المراحل السابقة).
2. أنشأت قاعدة بيانات فارغة جديدة تمامًا (كأنها خادم جديد بعد كارثة).
3. استعدت النسخة الاحتياطية فيها.
4. قارنت **كل الأرقام** بين الأصل والنسخة المستعادة: تطابقت **بالضبط** (نفس عدد الصفوف بكل جدول، ونفس إجمالي المبالغ المدينة بكل القيود المحاسبية — 108,001.8460 دينار بالضبط بالجهتين).
5. تأكدت كمان إن قواعد الحماية بين الشركات (Row-Level Security) رجعت هي كمان صحيحة بعد الاستعادة، مش بس البيانات.

**يعني عمليًا**: لو صار أي كارثة (تلف قاعدة البيانات، خطأ بشري، مشكلة بالخادم)، عندك طريقة مثبتة فعليًا لاسترجاع كل بيانات الشركة كاملة بدون أي فقدان.

### د) كلمة سر مستخدم التطبيق (app_user) — خطوة أمان لازم تصير أول تشغيل حقيقي
قاعدة البيانات بتنشئ تلقائيًا مستخدم خاص بالتطبيق اسمه `app_user` (هو المستخدم المحدود الصلاحيات يلي التطبيق فعليًا بيتصل فيه، مش المستخدم الرئيسي الكامل الصلاحيات). أول ما تُنشأ قاعدة البيانات، كلمة سر هاد المستخدم بتكون قيمة معروفة بالكود (`change_me_in_production`) — لازم تغيّرها فورًا بعد أول تشغيل حقيقي:
```bash
./scripts/rotate-app-user-password.sh "postgresql://postgres:PASSWORD@HOST:5432/accora" "كلمة-سر-قوية-عشوائية-جديدة"
```
ثم حدّث `RUNTIME_DATABASE_URL` بنفس الكلمة الجديدة وأعد تشغيل الخادم.

### هـ) جدولة النسخ الاحتياطي التلقائي
السكريبت جاهز للتشغيل عبر `cron` على أي خادم حقيقي، مثلاً نسخة كل يوم الساعة 3 فجرًا:
```
0 3 * * * DATABASE_URL="..." /path/to/scripts/backup.sh
```
(ما قدرت أجدولها فعليًا هون لأنه بيئة الجلسة الحالية مؤقتة وما بتضل موجودة — هاي خطوة تصير على الخادم الحقيقي وقت التشغيل الفعلي).
