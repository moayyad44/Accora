## 2. كيف تعمل نقطة الدخول الأساسية: `POST /auth/register-company`

هذا هو المسار الذي ينشئ شركة جديدة بالكامل بخطوة واحدة:

1. يتحقق أن البريد الإلكتروني غير مستخدم من قبل.
2. ينشئ المستخدم (مع تشفير كلمة المرور).
3. ينشئ الشركة.
4. **يستنسخ دليل الحسابات الافتراضي (58 حساب)** من القالب العام إلى حسابات خاصة بهذه الشركة فقط — قابلة للتعديل الكامل من اللحظة الأولى.
5. **يستنسخ الأدوار العشرة القياسية** (مدير النظام، محاسب، مبيعات...) مع صلاحياتها إلى أدوار خاصة بهذه الشركة.
6. يربط المستخدم كـ"مدير النظام" (Company Admin) في هذه الشركة.
7. كل هذا داخل معاملة واحدة (Transaction) — إما ينجح بالكامل أو يفشل بالكامل، لا يوجد احتمال "شركة نصف مُنشأة".

**تم التحقق فعليًا**: تسجيل شركتين منفصلتين، كل شركة حصلت على 58 حساب و10 أدوار خاصة فيها بشكل مستقل تمامًا (Company A ≠ Company B، لا تداخل إطلاقًا).

## 3. عزل الشركات على مستوى التطبيق الفعلي — ليس فقط قاعدة البيانات

في Phase 2 أثبتنا أن قاعدة البيانات نفسها (PostgreSQL RLS) ترفض قراءة بيانات شركة أخرى. في Phase 3 أثبتنا أن **الكود الفعلي (السيرفر) يستخدم هذه الحماية بشكل صحيح**، وهذا فرق جوهري:

- السيرفر لا يتصل بقاعدة البيانات كـ"مستخدم خارق" (`postgres`) الذي يتجاوز كل الحمايات تلقائيًا. يتصل بحساب محدود الصلاحيات (`app_user`) هو نفس الحساب الذي تخضع له سياسات RLS — إذا نسي المبرمج فلترة أي استعلام مستقبلًا، قاعدة البيانات نفسها ستمنعه، وليس فقط "نية حسنة" بالكود.
- كل طلب HTTP مصادق عليه يفتح معاملة قاعدة بيانات واحدة تُحدَّد فيها "أنا أتصرف نيابة عن الشركة كذا والمستخدم كذا" قبل أي استعلام.
- **تم التحقق عبر اختبار آلي حقيقي**: مدير الشركة A حاول التبديل إلى الشركة B (يلي ما إله صلاحية عليها) → **رُفض الطلب (403)**. طلب لقائمة مستخدمي الشركة بحساب مدير الشركة A رجّع مستخدمي الشركة A فقط، رغم وجود الشركة B ومستخدميها بنفس قاعدة البيانات.

## 4. الصلاحيات (RBAC) — تم التحقق أنها فعلاً تمنع، وليس فقط موجودة بالتصميم

كل عملية بالنظام (مثال: "عرض قائمة المستخدمين") مربوطة بصلاحية محددة (`core.user.view`). عند كل طلب، النظام يتحقق **من قاعدة البيانات مباشرة** (وليس من التوكن المخزّن) هل دور هذا المستخدم يملك هذه الصلاحية فعلًا — يعني لو سحبت صلاحية من دور معيّن، القرار ينعكس فورًا على كل طلب جديد، بدون انتظار انتهاء صلاحية جلسة الدخول.

**تم التحقق فعليًا**: أنشأنا مستخدمًا بدور "مبيعات" (Sales) فقط داخل الشركة A، وحاولنا نطلب منه قائمة المستخدمين (عملية تحتاج صلاحية إدارية) → **رُفض الطلب (403) برسالة واضحة تحدد الصلاحية الناقصة**. بينما نفس الطلب بحساب "مدير النظام" نجح بشكل طبيعي.

## 5. نقاط الدخول (Endpoints) الجاهزة في Phase 3

| العملية | Endpoint | يحتاج صلاحية؟ |
|---|---|---|
| تسجيل شركة جديدة + مدير | `POST /auth/register-company` | لا (مفتوح) |
| تسجيل الدخول | `POST /auth/login` | لا (مفتوح) |
| تبديل الشركة النشطة | `POST /auth/switch-company` | لا (فقط يتحقق من امتلاك صلاحية وصول) |
| تجديد جلسة الدخول | `POST /auth/refresh` | لا (مفتوح، يحتاج refresh token صالح) |
| بياناتي الشخصية | `GET /users/me` | لا (فقط تسجيل دخول) |
| قائمة مستخدمي الشركة الحالية | `GET /users` | نعم: `core.user.view` |
| الشركات التي أملك صلاحية عليها | `GET /companies` | لا (خاصة بهويتي دائمًا) |
| أدوار الشركة الحالية وصلاحياتها | `GET /roles` | نعم: `core.role.view` |

## 6. ملاحظة صريحة: ما تم تبسيطه في Phase 3 (وليس نسيانًا)

- استُخدم `bcryptjs` لتشفير كلمات المرور بدل `argon2` المذكور بالمعمارية الأصلية — قرار عملي لتفادي مخاطر تثبيت مكتبة تحتاج بناء برمجي (native compilation) قد تفشل في بعض بيئات النشر؛ bcrypt لا يزال معيارًا آمنًا ومعتمدًا صناعيًا (استُخدم بقوة تشفير 12). يمكن التبديل لـ Argon2 لاحقًا بسهولة (المكان الوحيد الذي يستخدمها هو `auth.service.ts`).
- لا يوجد بعد Endpoint لـ"دعوة مستخدم جديد لشركة موجودة" (Invite) — فقط "منشئ الشركة" يصبح تلقائيًا مديرًا لها. إضافة مستخدمين آخرين للشركة ستُبنى في مرحلة لاحقة قريبة.
- `refresh token` لا يحمل معلومة "أي شركة كنت أعمل عليها" (بقصد، لأسباب أمنية — صلاحية الوصول للشركة قد تتغير)، فبعد تجديد الجلسة يحتاج المستخدم لاختيار شركته من جديد عبر `switch-company`. تفصيل بسيط لا يؤثر على تجربة استخدام حقيقية (الواجهة تقدر تخزن آخر شركة مختارة وتستدعي switch-company تلقائيًا).
