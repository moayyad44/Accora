## 0. أولًا: تأكيد على مبدأ "الإعدادات التلقائية القابلة للتحكم"

هذا المستند نفسه يحتوي مثال إضافي ملموس على المبدأ يلي أكدت عليه: أثناء بناء تتبع الدفعات (Batch)، اكتشفت (عبر الاختبار الآلي نفسه، قبل ما توصل لأي مستخدم) إنه **طريقة تقييم المخزون لصنف معيّن ما كانت قابلة للتحديد من واجهة الـ API إطلاقًا** — كانت موجودة بقاعدة البيانات بس ما في طريقة تغييرها إلا بالوصول المباشر لقاعدة البيانات. صلّحتها فورًا: هلق `POST /catalog/items` بيقبل `valuationMethodOverride` اختياري — يعني **أي شركة تقدر تخلي صنف معيّن يستخدم FIFO حتى لو باقي الشركة على المتوسط المرجح** (مثال منطقي: شركة أغذية عامة على المتوسط المرجح، بس منتجاتها الحساسة لتاريخ الصلاحية تحتاج FIFO تحديدًا). هذا بالضبط نوع الإعداد يلي المفروض يكون "افتراضي بس قابل للتخصيص لكل صنف لحاله".

## 1. الجرد (Stock Count) — دورة كاملة

| العملية | Endpoint |
|---|---|
| إنشاء جرد (يلتقط الأرصدة الحالية تلقائيًا كنقطة بداية) | `POST /inventory/stock-counts` |
| تسجيل الكميات الفعلية المعدودة | `PATCH /inventory/stock-counts/:id/counted-quantities` |
| ترحيل الجرد | `POST /inventory/stock-counts/:id/post` |
| قائمة/عرض عمليات الجرد | `GET /inventory/stock-counts`, `GET /inventory/stock-counts/:id` |

**كيف بيشتغل**: تنشئ جرد لمستودع معيّن (جرد شامل لكل الأصناف، أو جرد جزئي لأصناف محددة فقط عبر `itemIds`) — النظام ياخد "صورة" لكل الكميات يلي بيقول النظام إنها موجودة حاليًا. تسجّل الكميات الفعلية يلي عددتها. لما ترحّل:
- كل الأصناف يلي ما فيها فرق (العدد الفعلي = العدد بالنظام) **ما بتولّد أي حركة أو قيد** — فقط الفروقات الحقيقية بتتحرك.
- **كل فروقات الجرد كله بتترحل بقيد محاسبي واحد** (مش قيد لكل صنف) — جرد فيه 50 صنف وفيه 3 فروقات بس، بينتج قيد وحدة فيه أثر الـ 3 فروقات مع بعض.

**تم التحقق فعليًا**: جرد وجد نقص 3 قطع (كان بالنظام 20، الفعلي 17) — القيد المحاسبي طلع بالضبط بقيمة 15 دينار (3 × 5 دنانير تكلفة الوحدة)، والرصيد تصحح لـ 17. وجرد ثاني بدون أي فرق — ترحّل بدون أي قيد محاسبي إطلاقًا (لأنه ما في شي تغيّر فعليًا).

## 2. تتبع الدفعات (Batch/Lot) وتاريخ الصلاحية

| العملية | Endpoint |
|---|---|
| دفعات صنف معيّن مع الكمية المتبقية لكل دفعة | `GET /inventory/items/:itemId/batches` |
| الدفعات القريبة من انتهاء الصلاحية (كل الأصناف) | `GET /inventory/expiring-batches?withinDays=30` |

**كيف بيشتغل**: أي صنف تحدد له `trackingType: "BATCH"`، لما تستلمه بفاتورة شراء **لازم** تحدد رقم الدفعة (وتاريخ الصلاحية اختياري) — النظام بيرفض الفاتورة لو نسيت. كل دفعة بتحتفظ بتكلفتها الخاصة فيها وتاريخ صلاحيتها، وتقدر أي وقت تسأل "شو الدفعات يلي راح تنتهي خلال 30 يوم؟" لكل الأصناف مرة وحدة — مفيد جدًا لتنبيه "قرب انتهاء صلاحية صنف" يلي طلبته بمتطلبات الإشعارات.

**تم التحقق فعليًا**: استلمت دفعة برقم مميز وتاريخ صلاحية بعد 5 أيام — ظهرت فورًا بقائمة "الدفعات المنتهية قريبًا"، وبالكمية المتبقية الصحيحة.

**ملاحظة دقة مهمة (موثّقة بالكود نفسه)**: تتبع "الكمية المتبقية لكل دفعة" بدقة تامة يشتغل فقط إذا كان الصنف بيستخدم تقييم FIFO (لأنه هذا بالضبط أسلوب FIFO — طبقات تكلفة منفصلة بيوثقها النظام أصلاً). لو الصنف على المتوسط المرجح، النظام لسا بيسجل رقم الدفعة وتاريخ الصلاحية بشكل صحيح عند الاستلام، بس "الكمية المتبقية لكل دفعة تحديدًا" ما بتكون دقيقة (لأنه المتوسط المرجح أصلاً بيخلط كل الكميات مع بعض بدون تمييز). هذا مش خطأ، هذا طبيعة الفرق بين الطريقتين — وثّقته بوضوح بالكود حتى ما حدا يتفاجئ.

## 3. تتبع الأرقام التسلسلية (Serial Numbers)

| العملية | Endpoint |
|---|---|
| الأرقام التسلسلية المتوفرة حاليًا لصنف معيّن | `GET /inventory/items/:itemId/serials` |

**كيف بيشتغل**: أي صنف `trackingType: "SERIAL"` (زي أجهزة إلكترونية، معدات — كل وحدة فريدة من نوعها) — كل رقم تسلسلي بيتعامل معه النظام كوحدة مستقلة تمامًا إلها هويتها الخاصة.

**نقطة محاسبية مهمة**: الأصناف التسلسلية **ما بتُقيّم بـ FIFO ولا بالمتوسط المرجح إطلاقًا** — بتُقيّم بطريقة "التحديد المحدد" (Specific Identification)، يعني كل وحدة بتكلّف بالضبط بالسعر يلي اتشرت فيه هي بالذات، مش بمتوسط أو بترتيب الشراء. هاي فعليًا الطريقة المحاسبية الصحيحة للأصناف عالية القيمة يلي كل وحدة فيها مميزة (منصوص عليها بالمعايير المحاسبية تحديدًا لهذا النوع من المخزون).

**تم التحقق فعليًا**: اشتريت جهازين بسعرين مختلفين (800 و850 دينار)، وبعت الجهاز يلي كلف 850 بالتحديد — تكلفة البضاعة المباعة طلعت بالضبط 850 دينار، **مش المتوسط (825)**. جربت أبيع نفس الرقم التسلسلي مرة ثانية (بعد ما انباع) → النظام رفض العملية لأنه "مو متوفر حاليًا بالمخزون".
